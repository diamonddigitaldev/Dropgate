# Building and Testing

Requires Node.js 24 or later. From `packages/dropgate-core`:

```bash
npm ci
npm run typecheck
npm run build
npx vitest run
```

The Dropgate Server's Web UI and the Dropgate Client load core's ESM build as their own copy, [`server/public/js/dropgate-core.js`](../../server/public/js/dropgate-core.js) and [`client/src/dropgate-core.js`](../../client/src/dropgate-core.js). `npm run build` writes both ([`scripts/copy-build.mjs`](../../packages/dropgate-core/scripts/copy-build.mjs)). They're committed, so the server, its Docker image and the client run and package without building core first. After changing core, build it and commit the copies with the change, and never edit them by hand. `npm run dev` only rebuilds `dist/`.

Tests for known issues are marked `it.fails`, and vitest counts them as "expected fail". Each one only counts as expected while it fails in the specific way its issue causes, so it fails once the issue is fixed, or if something else breaks it, and the marker can't be forgotten. Each test's name says what fixes it. To list them all:

```bash
npx vitest run --reporter=verbose
```

The tests run in plain Node, with no browser environment. The P2P tests use stand-ins for the PeerJS objects (core's [`tests/helpers/fake-peer.ts`](../../packages/dropgate-core/tests/helpers/fake-peer.ts)), and most client tests use a fake server passed in as `fetchFn`. [`tests/hosted.test.ts`](../../packages/dropgate-core/tests/hosted.test.ts) runs against the real Dropgate Server instead, started by the server tests' own harness in a temporary folder on `127.0.0.1`, so install the server's dependencies first (`npm ci` in `server/`). No test reaches beyond your machine, or needs a PeerJS server. The Web UI and the Dropgate Client are tested in real browsers and Electron by the [integration tests](../../tests/integration/README.md).

Core's crypto is checked against published known answers, on both of its crypto providers, Web Crypto and `@noble` ([Crypto](crypto.md)). CPace, the exchange a typed code will run, is pinned by its own draft's test vectors, draft-irtf-cfrg-cpace-21's Appendix A.1, A.3, B.1 and B.1.10 (the generator, both shares, the shared point, both session keys, the session-ID output and the low-order points that must abort), copied from the draft's own JSON into [`tests/fixtures/cpace-x25519-sha512-vectors.json`](../../packages/dropgate-core/tests/fixtures/cpace-x25519-sha512-vectors.json), which says where each value came from. [`tests/cpace-exchange.test.ts`](../../packages/dropgate-core/tests/cpace-exchange.test.ts) runs the exchange itself, on each provider and with one side on each: its key confirmation checked against `node:crypto` working from the formula rather than from core's code, every abort (a wrong code, a share of the wrong length or of low order, a confirmation that doesn't match) ending both sides with `CODE_MISMATCH`, a code used only once, each secret overwritten once used, and a failed exchange's messages holding nothing a guess at the code could be checked against. [`tests/codes.test.ts`](../../packages/dropgate-core/tests/codes.test.ts) checks how codes are drawn, byte by byte, and draws a million to check every place's letters and digits for bias with a chi-squared test. Noise, the encrypted handshake and records a direct transfer will run over its connection (`Noise_NNpsk0_25519_AESGCM_SHA256`), is pinned by the one published vector for that exact name, from [cacophony](https://github.com/haskell-cryptography/cacophony)'s `vectors/cacophony.txt` at commit `8ee9d41` (public domain, under the Unlicense), copied unchanged into [`tests/fixtures/noise-cacophony-vector.json`](../../packages/dropgate-core/tests/fixtures/noise-cacophony-vector.json) with its source: both handshake messages, the handshake hash and four transport messages. No published vector covers Noise's rekeying, so Dropgate's own, in [`tests/fixtures/noise-rekey-vectors.json`](../../packages/dropgate-core/tests/fixtures/noise-rekey-vectors.json), come from [`tests/helpers/reference-noise.mjs`](../../packages/dropgate-core/tests/helpers/reference-noise.mjs), a second implementation on `node:crypto` written from the Noise specification (revision 34) rather than from core's code, which passes cacophony's vector too: a run past 65,536 records each way and runs with the interval lowered, with the key after each rekey (`node tests/helpers/reference-noise.mjs` writes them again). [`tests/noise.test.ts`](../../packages/dropgate-core/tests/noise.test.ts) runs both on each provider, a handshake with one side on each, and Noise's limits: the largest record and handshake payload, a flipped bit anywhere, and the end of the nonces. Pinning an ephemeral key or lowering the rekey interval is only possible in a test build: vitest's config and the browser check's bundle define `__DROPGATE_TEST_BUILD__` as `true`, every one of core's builds as `false` ([`scripts/test-build-define.mjs`](../../packages/dropgate-core/scripts/test-build-define.mjs)), and a test bundles core's Noise as the builds do and checks that it refuses both. Nor does any published vector cover what Dropgate builds on top: the key schedule that makes every key of a direct transfer's attempt from its one secret (a link's, a typed code's or a resume's), and the sealed, padded messages that set up its connection through the server. Their vectors, in [`tests/fixtures/dgdtp-signal-vectors.json`](../../packages/dropgate-core/tests/fixtures/dgdtp-signal-vectors.json), come from [`tests/helpers/reference-signal.mjs`](../../packages/dropgate-core/tests/helpers/reference-signal.mjs), another second implementation on `node:crypto` written from the format rather than from core's code: every output of the key schedule from fixed inputs, by link, by code and on resume, and each kind of message each way, in each of the three padded sizes (`node tests/helpers/reference-signal.mjs` writes them again). [`tests/signal.test.ts`](../../packages/dropgate-core/tests/signal.test.ts) checks core makes exactly those bytes on each provider, and that every message that isn't the next one expected ends the attempt: every bit of a message flipped, one replayed, reordered or skipped, one from another attempt, one sent back to the device that sealed it, one sealed under the right key but holding anything but exactly a message, and the 4,097th one way; and that every candidate is the same size whatever kind of address it holds. What ties the encrypted handshake to the connection it runs over, the prologue that holds both devices' certificate fingerprints, has its vectors in [`tests/fixtures/dgdtp-prologue-vectors.json`](../../packages/dropgate-core/tests/fixtures/dgdtp-prologue-vectors.json), from [`tests/helpers/reference-prologue.mjs`](../../packages/dropgate-core/tests/helpers/reference-prologue.mjs), written the same way, on `node:crypto` from the format: the fingerprint each of 18 SDPs gives or the reason it's refused (none, two different, or one that isn't one), the prologue by link, by code and on resume up to the last generation, and a whole handshake over one, from its offer and answer to Noise's two messages and its hash (`node tests/helpers/reference-prologue.mjs` writes them again). [`tests/prologue.test.ts`](../../packages/dropgate-core/tests/prologue.test.ts) checks core reads and builds exactly those, that both sides build the same prologue, and that a change to any bit of either fingerprint, or to any other field, changes it. [`tests/channel.test.ts`](../../packages/dropgate-core/tests/channel.test.ts) runs a direct transfer's secure channel end to end, on each provider and with one side on each, over a mock server and fake connections with fake SDP ([`tests/helpers/fake-channel.ts`](../../packages/dropgate-core/tests/helpers/fake-channel.ts)), with no WebRTC: by link, by code and on resume, the two sides' keys and handshakes matching the second implementations', every random value and key fixed to give the handshake vector's bytes; a wrong code ending both sides with `CODE_MISMATCH` in each one's own words, and of a code only its locator leaving the device; a fingerprint swapped in the set-up by something holding its keys ending both sides with `SECURITY_POLICY_MISMATCH`, with nothing sent after the handshake's first message; a handshake message, a first record or a set-up message that isn't exactly what it must be ending the attempt; the out-of-band close each way; and every key let go and nothing secret logged, whatever ends it. X25519, SHA-256, SHA-512, HMAC, HKDF and AES-GCM with associated data are checked against RFC 7748, FIPS 180-4, RFC 4231, RFC 5869, the GCM specification's own test cases, a NIST AES-256-GCM vector, and Project Wycheproof's AES-256-GCM tests with a 96-bit IV, in [`tests/fixtures/wycheproof-aes-gcm-256.json`](../../packages/dropgate-core/tests/fixtures/wycheproof-aes-gcm-256.json) (which says where they came from). [`tests/crypto.test.ts`](../../packages/dropgate-core/tests/crypto.test.ts) also gives both providers the same random inputs and checks they give the same bytes, and [`tests/object.test.ts`](../../packages/dropgate-core/tests/object.test.ts) makes DGUP 4's object vectors on each and opens each one's objects with the other. [`tests/provider-choice.test.ts`](../../packages/dropgate-core/tests/provider-choice.test.ts) checks which provider core chooses: Web Crypto in Node, every operation on it, with a spy showing `@noble`'s provider is never made; `@noble` for everything with no `crypto.subtle`, or one that can't make an X25519 key, with nothing more reaching `crypto.subtle` after the one probe. The CPace, CPace exchange, Noise, sealed message, secure channel and provider checks ([`tests/helpers/cpace-vectors.ts`](../../packages/dropgate-core/tests/helpers/cpace-vectors.ts), [`cpace-exchange-checks.ts`](../../packages/dropgate-core/tests/helpers/cpace-exchange-checks.ts), [`noise-vectors.ts`](../../packages/dropgate-core/tests/helpers/noise-vectors.ts), [`signal-checks.ts`](../../packages/dropgate-core/tests/helpers/signal-checks.ts), [`channel-checks.ts`](../../packages/dropgate-core/tests/helpers/channel-checks.ts) and [`provider-vectors.ts`](../../packages/dropgate-core/tests/helpers/provider-vectors.ts)) also run in Chromium, Firefox and WebKit, through the integration tests' [`core/crypto-vectors.spec.mjs`](../../tests/integration/core/crypto-vectors.spec.mjs), on the provider core chooses in each engine (Web Crypto in Chromium and Firefox, and in WebKit where it has X25519; `@noble` in Playwright's WebKit on Windows, which has none) and on `@noble` in all three, so every browser engine is held to the same bytes as Node. Each test records the provider chosen.

`@noble/curves`, `@noble/hashes` and `@noble/ciphers` are dev dependencies pinned to an exact version, compiled into every build (ESM, CommonJS, the browser bundle and the two copies below), so core's package still lists no runtime dependencies. Every build starts with their MIT notice, written from their LICENSE files by [`scripts/third-party.mjs`](../../packages/dropgate-core/scripts/third-party.mjs), and [`THIRD-PARTY-NOTICES.md`](../../packages/dropgate-core/THIRD-PARTY-NOTICES.md), in the package, has each licence in full (`npm run notices` writes it again). [`tests/build.test.ts`](../../packages/dropgate-core/tests/build.test.ts) checks, after `npm run build`, that no build file imports `@noble/`, that each holds its code and the notice, that the notices file matches the installed licences, that the pins match the lockfile, and that [Crypto](crypto.md)'s audit table names the same versions. A dependency update that moves `@noble` updates that table too: its versions, the audits as each package's README lists them, and the date checked.

A direct transfer's secure channel also runs over real WebRTC in Node. [`tests/webrtc.test.ts`](../../packages/dropgate-core/tests/webrtc.test.ts) runs it through core's WebRTC adapter ([`src/dgdtp/webrtc.ts`](../../packages/dropgate-core/src/dgdtp/webrtc.ts)) on werift's `RTCPeerConnection`, both devices in one process with real DTLS between them, through the mock server: by link, by code and on resume, each device's prologue built from the one SHA-256 fingerprint in the SDP it applied, which is its certificate's; a record of 65,535 bytes crossing each way intact, and one byte more refused; `writable()` resolving by looking at the buffer when no `bufferedamountlow` event comes (werift never fires one); the data channel closing under either device ending both with `CONNECTION_LOST`; and a relay in the middle, two peer connections of its own back to back, holding the set-up's keys as a malicious server that had them would, terminating DTLS on both sides with its own certificates and putting its fingerprints in the set-up. Both devices end with `SECURITY_POLICY_MISMATCH`, and nothing but the handshake's first message and the abort crosses. The same file checks the adapter over a stand-in `RTCPeerConnection` for what werift can't show: text messages, a channel of another name, the max-message-size's sources, ICE failing, and `writable()` on the event. werift is a dev dependency pinned to an exact version, and `tests/build.test.ts` checks no build imports it, or node-datachannel. Two of werift's defaults are set aside in these tests, so nothing leaves your machine: given no ICE servers, werift still asks Google's STUN server (`stun.l.google.com`) from every IPv4 address, so ICE runs on IPv6's loopback address, `::1`, alone, where it asks none; and werift gives every peer connection in a process the same DTLS certificate, so each one here gets its own. No test makes a `.local` candidate, which werift would look up with an mDNS query on the local network.

DGUP 4's encrypted object (its header, keys, chunks, padding and file list) is pinned byte for byte in [`tests/fixtures/dgup4-object-vectors.json`](../../packages/dropgate-core/tests/fixtures/dgup4-object-vectors.json). The vectors were made by [`tests/helpers/reference-object.mjs`](../../packages/dropgate-core/tests/helpers/reference-object.mjs), a second implementation on `node:crypto`, written from the format rather than from core's code. Core's tests check that both make exactly those bytes, and anything else that builds the object, such as the server's tests, can be checked against the same file.

Core's ZIP writer is tested two ways. [`tests/zip.test.ts`](../../packages/dropgate-core/tests/zip.test.ts) reads each archive back with a reader of its own, written from PKWARE's format description rather than from the writer, including one member of 4 GiB + 1 byte, offsets past 4 GiB and 65,535 members, which take about 6 seconds between them. Runs of zeros are recorded as their length, so those archives never sit in memory. In GitHub Actions, readers that aren't core's then check the same kinds of archive whole: [`tests/zip-readers/write-archive.mjs`](../../packages/dropgate-core/tests/zip-readers/write-archive.mjs) writes each with the build, and Info-ZIP's `unzip -t` and [`check_archive.py`](../../packages/dropgate-core/tests/zip-readers/check_archive.py), on Python's `zipfile`, read it back. To run them yourself, after `npm run build` (two of the archives are over 4 GiB, written one at a time):

```bash
node tests/zip-readers/write-archive.mjs member-4gib /tmp/zips
unzip -tq /tmp/zips/member-4gib.zip
python3 tests/zip-readers/check_archive.py /tmp/zips/member-4gib.zip /tmp/zips/member-4gib.json
```

The kinds are `classic`, `member-4gib`, `offsets-4gib` and `members-65536`.

Core's [`tests/copies.test.ts`](../../packages/dropgate-core/tests/copies.test.ts) checks that the server's and the client's copies are the build in `dist/`, so run it, and `tests/build.test.ts`, after `npm run build`.

[`tests/dgdtp-doc.test.ts`](../../packages/dropgate-core/tests/dgdtp-doc.test.ts) holds the table of the secure channel's constants in [DGDTP §4.14](../technical/DGDTP.md#414-constants) to the values in core's code, both ways: every constant the table names has the value it gives, and none is missing from it.

Outside the repository, for example unpacked from a release's `dropgate-core-<version>.tar.gz`, there are no copies and no docs. The build then says so and writes no copies, and their tests and the constants' test are skipped. A test that always runs checks this only happens when the server's and the client's copies aren't there.

GitHub Actions runs these steps on Ubuntu ([`ci.yml`](../../.github/workflows/ci.yml)). It fails if the build changes either copy: that means a copy was edited by hand, or not built again after a change to core. The release workflow also runs them in core's source archive, unpacked on its own, and then stages the package on npm with provenance, through npm's trusted publishing, so no npm token is kept in GitHub. A staged version isn't on npm until a maintainer approves it there, with two-factor authentication. The workflow's dry run runs npm's dry run of publishing instead ([Releases](../../README.md#releases)).

Core shares its version with the server and the client, and they're released together ([Releases](../../README.md#releases)). Change it in `package.json`, `package-lock.json` and the version badge at the top of [core's README](../../packages/dropgate-core/README.md) together, or GitHub Actions fails.
